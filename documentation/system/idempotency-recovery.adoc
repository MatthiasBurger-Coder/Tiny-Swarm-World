= Idempotency and recovery contract (ARCH-03.13)

This contract describes the implemented Classic Docker Swarm paths. A rerun is
permitted only after the operator inspects the failed target and confirms its
current state. Live mutation still requires the existing consent path. Local
tests do not establish live recovery.

== Common rules

* Validation, authorization, missing input, unsupported configuration and
  ownership mismatches are non-retryable until corrected. An interrupted or
  timed-out mutation has an unknown effect; it is not automatically retried.
* Read-only observation may be retried within the existing bounded verification
  attempts. A failed observation cannot be interpreted as an absent resource.
* A mutation is successful only to the level established by its documented
  verification. Docker stack command completion establishes command acceptance,
  not service convergence or readiness.
  `executed=true` means a command was attempted, not that the effect is known.
  Earlier verified steps remain visible in workflow verification results when a
  later step fails. The failed target and its effect remain unresolved until
  observed again.
* Generic recovery never deletes a shared network, an external Swarm secret,
  a stack, or its persistent volumes as automatic compensation. The owned
  Traefik TLS pair is a narrow exception described below. Post-create cleanup
  failure is reported alongside the original error.

a foreign pair is never replaced.

|Portainer service-stack apply and Docker stack deploy
|Ensure prerequisites, submit create/update or deploy, then verify registration
and, where configured, separate service readiness.
|A failed apply remains failed even if a stack name exists: an earlier version
may already be registered. A failed prerequisite stops before stack apply.
Workflow results retain prior verified targets and the failed target. A Docker
deploy command success is distinct from service readiness.
|Read-only verification is bounded. No automatic retry of create/update/deploy

stack and services before explicit rerun.
|No automatic stack removal or volume rollback. For the supported Classic

source plan and live consent; success requires observed source convergence.
|Create/update chooses by observed stack identity. Repeated Docker stack deploy
targets the same stack, but a no-op claim requires verification of the desired
service state; registration alone is insufficient.

|Configuration and Classic image update
|Configuration sources and Compose definitions are read and validated before
apply. Classic update stores a recovery plan, applies an image transition and
observes runtime convergence. The per-invocation image override does not edit
committed configuration.
|Invalid or unavailable configuration blocks before mutation. A failed apply
or failed convergence retains recovery state and reports a non-success result.
|Fix invalid input before rerun. For a failed/unknown image transition, inspect
the service and use the explicit recovery path; never blindly retry a second
transition.
|`platform recover` targets the original source image, preserves the original
recovery plan across retries, and reports success only after convergence. It is
not a backup or restore of service data.
|An already converged target is an observed no-op. Repeated successful recovery
does not reverse the original plan again. Configuration reads have no mutation.

== Failure classification and operator sequence

`retryable` means a read-only observation may be repeated within its bounded
budget, or an operator may explicitly rerun a mutation after state inspection.
It never authorizes a blind automatic mutation retry. Missing/invalid input,
unsafe ownership, contradictory observed state and permanent rejection require
repair. Transport timeout or interrupted response leaves the mutation effect
unknown. A failed verification is distinct from a failed apply.
The LXC shell gateway requires explicit `retry_safe=True` for its bounded
transient transport retry; mutating callers use the default of no transport
retry. A transient Incus child-PID failure does not prove the script had no
effect.

After any failed mutation, retain the workflow result and verification evidence,
inspect the target read-only, compare it with the desired input, and choose an
explicit rerun or supported recovery. Where observation is unavailable, stop
and report the unresolved state. Do not label a compensation attempt as rollback
success without an observed restoration. Secrets and private diagnostic data
must remain out of logs and evidence.

The shared operation-result contract from issue #355 is present in the
deployment workflow. It reports a typed outcome and failure alongside the
existing workflow status and verification results. These records preserve
known completed and failed steps; they cannot prove every low-level side
effect of a timed-out command.
