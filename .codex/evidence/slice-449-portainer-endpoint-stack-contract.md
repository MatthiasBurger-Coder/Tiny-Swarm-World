Endpoint pagination/visibility guarantees and the assertion that a 404/405 create response proves no mutation are also unverified. No positive full-inventory assertion is permitted on that evidence. The former create-on-apparent-absence and 404/405 fallback requirements below are historical proposals, not executable authorization: do not create based on that listing, do not retry an uncertain create, and do not treat 404/405 as proof of no effect. A future supported authoritative source or a server-side conditional identity/write primitive may enable broader behavior only after its actual visibility, identity and failure semantics are independently demonstrated. No candidate is approved merely by listing it here. ## Endpoint and stack resolution

For each apply, obtain a complete, successfully decoded endpoint inventory and select exactly one existing endpoint by exact configured endpoint name and a unique positive integer ID (`type(value) is int`; boolean, numeric strings, zero/negative, duplicates, missing or malformed IDs reject). Existing local fallback may only remain if a single unambiguous local candidate is provable under an explicitly tested existing rule; multiple candidates, conflicting exact names/fallback, malformed endpoint entries or unknown inventory completeness block. Do not create or repair an endpoint as part of apply. If endpoint identity, list completeness or local fallback authority cannot be established without guessing, stop/fail closed rather than select first. Do not expand accepted endpoint rules or log endpoint data.

Use the existing authentication POST `/api/auth` and read-only endpoint/stack inventory GETs as necessary before validation. Authentication is permitted and must retain its current behavior. The adapter must establish completeness using the actual API response contract; unsupported pagination, filtering, authorization-limited visibility, truncation or any other inability to establish a complete inventory is UNKNOWN and fails closed. Do not infer absence from an incomplete response. Read a complete stack listing with strict schema: each relevant record has an exact name, positive integer stack ID and positive integer `EndpointId`, no booleans/coercion. Missing/malformed record, non-list/partial response or an API/list pagination/completeness uncertainty must block, not mean absent. For the target name, a same-name record on any other endpoint, more than one same-name record, duplicate IDs or malformed/conflicting records yields fixed safe `PortainerClientError` before effects. A single same-name record at the exact selected endpoint gives the candidate stack ID. Create is permitted only after a complete valid list proves no same-name stack on any endpoint. Record inventory evidence in memory only; no raw response, URL, token, credential or exception is logged.

Immediately before the first mutating stack or network effect repeat endpoint and stack lookup and require identical `(endpoint_id, stack_id or ABSENT)` state. The LXC path must do this **before** `_ensure_external_overlay_networks`, network-creating manager commands, and mutating stack POST/PUT; direct path before mutating stack POST/PUT. Authentication POST and read-only inventory GETs remain permitted before the validated recheck. A changed or unreadable identity blocks. Subsequent effect has a non-atomic gap: no Portainer CAS or race-free ownership guarantee is asserted; concurrent changes after recheck may occur. A same-name foreign stack on the same endpoint may still match; this slice proves endpoint/name uniqueness only, not ResourceControl, persisted ownership, expected definition, writer identity or real convergence. A later separately reviewed persisted ownership + endpoint/stack/ResourceControl/definition identity guard is mandatory for full optional-stack admission.

No host/network action is executed during testing; use mocks. Normal direct `update_stack` port calls remain out of this guard's scope and must not be advertised as guarded. Do not silently route `stack_registered` to a weaker result as proof of ownership. Existing create fallback 404/405 remains subject to the same pre-effect resolution and must not retry an uncertain create result or claim atomicity. If changes to the port or wrappers are needed, update all interface implementations and existing test fakes; preserve unrelated legacy command contracts and no-prune update payload.
