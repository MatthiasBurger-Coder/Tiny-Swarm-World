Define a distinct strict `InstallationManifestV2` based on/reusing the canonical validated shared fields and invariant logic, so schema 1 remains accepted exactly as before; do not broaden its Literal[1] or change v1 decoder semantics. ## Closed domain and conversion rules

1. Inputs are an explicit strict validated schema-1 `InstallationManifest`, validated schema-1 `ComponentCatalog` and explicit typed supplied binding inputs. Revalidate even `model_construct`/`model_copy` values; reject unknown schema/catalog versions, extra fields, aliases or duplicate keys at any parsing boundary, duplicate service/component/route/stack IDs, inconsistent catalog, forged data, missing fields, booleans where integer required and malformed inputs. No JSON parser or filesystem access is added here; duplicate serialized keys remain the responsibility of the existing parser, which stays unchanged.
2. Preserve every v1 field value, selection, order, provenance, component records, product/configuration/credential references, operation and checkpoint references without mutation, resolution, substitution, inferred secrets or data loss. Reuse existing G2a catalog validation and policy where safe without serializing its `v1_snapshot` to untrusted output. Explicit deterministic conversion returns a separately typed plan containing a valid strict v2 candidate, never writes or adopts. Repeated equivalent inputs yield equivalent plans.
3. Apply policy defaults: each selected optional catalog kind `stack` maps exactly once to `swarm`, ordered deterministically; selected `swagger` must be a stack and receives `published`; if absent, represent it explicitly as not selected rather than introducing a service. Never infer Portainer ownership or endpoint/stack/ResourceControl/fingerprint. An explicit supplied binding may be structurally checked but cannot establish real-world ownership; domain v1 conversion accepts only the `swarm` default. A future Portainer-capable schema/operation requires separate scope, validation and actual ownership proof before use.
4. Require explicitly supplied typed project, profile and complete route set. Project must be exactly `default`; profile identity must satisfy the accepted name grammar and binding to the supplied installation identity, and route tuples must use the existing `domain/network/lxc_proxy_device_plan.py:LxcProxyDevicePlan` validated representation or a reviewed exact canonical equivalent, including device, listen and connect identity. Reject UNKNOWN, absent, duplicate, ambiguous or invalid identities and incomplete/mismatched route sets; an explicit empty route set is admissible only if the separately supplied pure selection-derived expected set is also empty. Do not infer a route or use G2a UNKNOWN placeholders as valid v2 data. The precise typed binding and equality to authoritative pure selection-derived expected routes must be reviewed against existing code before implementation; if that cannot be derived without IO or inventing ownership, this slice BLOCKS rather than guesses. Structural validation establishes only internal consistency, not that a profile, route or host actually exists or belongs to TSW.
5. The plan cannot mutate live services, files, source objects or support registry. The v2 object is a domain value only, not admission or proof. A subsequent separately reviewed slice must specify JSON decode/persistence compatibility, lock/checkpoint and consent/JIT/GO before any write; actual runtime ownership and complete route observations require independent verification.

## P0 decision candidate: exact source inventory and closed input/output

This is a candidate for independent Requirement, Architecture, Security, Tester and DevOps decision, not accepted policy, executable slice or host authorization. Concrete source facts at baseline `d2fbc06e6f1cfce51bce557499427c9d8c548c9d`:

* `service_stack_contract.py` assigns selected stack `port_ids`; Portainer has `portainer-http`. `PortRegistry` / `infra/config/ports.yaml` maps that ID to TCP internal 9000 and external 10001. The former is a container/service port. The legacy Portainer proxy target is `127.0.0.1:10001`, distinct from container port 9000; this historical mapping does not independently establish an installation-owned live endpoint.
* `default_setup_manifest` always defines Portainer 10001 but its `host_preflight_required` varies with centralized ingress; preflight scope is not a complete proxy-route authority. Nexus stack `port_ids` includes `nexus-docker-https`, which `ports.yaml` maps to internal 5001 / external 13501 and Nexus Compose publishes at 13501. Setup also includes 13501; it is not a missing port-ID mapping. Swagger published port IDs map to external 16080 and 16081; the accepted internal exposure decision suppresses those published routes.
* `LxcProxyDevicePlan` supplies loopback defaults and a generated `tsw-proxy-<port>` but does not carry `nat` or `proxy_protocol`; its normalization and integer check are unsuitable as a complete strict authority. Neither current catalog nor `PortRegistry` alone proves exact manager-side proxy connect port, complete device flags, ownership or live listeners.

Candidate immutable `RoutePolicyInputV1` contains: validated ordered resolved service IDs with selected exposure (`published|internal` where applicable); a versioned frozen catalog snapshot with unique services and exact `port_ids`; a versioned frozen port snapshot with one unique mapping per required port ID including protocol, externally visible port and applicability; and a versioned route-binding snapshot with explicit provenance state and, for every selected required ID, device name, listen address/port, connect address/port, `nat` and `proxy_protocol`. ## Further source reconciliation — Pulsar and documented proxy defaults

`default_setup_manifest` includes Pulsar Manager backend port 7750 for both centralized and noncentral cases, while `service_stack_contract.port_ids` omits it; legacy `_plans_from_manifest` consumes every `required_ports` item. Therefore the stock port-ID catalog alone cannot be claimed complete. Architecture/ADR review must decide whether a validated selection-specific pure `default_setup_manifest` can become scoped authority and reconcile 7750 explicitly; the separate P0a candidate is unverified-runtime and does not resolve this gap. [Official Incus proxy device documentation](https://linuxcontainers.org/incus/docs/main/reference/devices_proxy/) documents `bind=host`, `nat=false`, `proxy_protocol=false` defaults for its current documentation. Explicit use in a new policy is a proposal requiring independent decision; it does not establish exact-version behavior, fixture result or live support.
