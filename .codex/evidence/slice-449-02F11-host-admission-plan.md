## Retained contract analysis for any independently proposed successor

The following records why the rejected F11 hypothesis lacks a verified implementation contract. Do not implement or connect to either bus or service socket under F11. A distinct successor would require all blockers below to have source-backed, tested solutions and fresh same-hash approval. The next task is a read-only specification and independently reviewed deterministic fixture, not a host diagnostic or client implementation:

1. **Authenticated manager and exact protocol.** Specify and justify the fixed system bus endpoint and its trust anchor, server authentication and peer verification, including socket/daemon ownership, cross-namespace behavior, and failure cases. Identify each exact D-Bus destination, object path, interface, method, property set and activation policy, including the bounded complete authentication and request bytes that will actually be sent. Fix message count, per-message and aggregate request/response byte limits, deadline and parser/schema before approval. A nominally read-only D-Bus query still sends bytes and may trigger activation or policy effects; prove those interactions acceptable in a deterministic fixture, or prohibit them. An unauthenticated endpoint, unknowable bus identity, uncontrolled activation, unknown wire bytes or unsupported manager API is a negative decision, not a reason to guess.
2. **Service socket side effects.** A Unix connect can activate a systemd socket, wake or change service state, consume capacity or have daemon-specific effects even if no payload is sent. Establish, from the exact unit/socket definitions and a deterministic fixture, the permitted endpoint and a non-activating or otherwise explicitly scoped and authorized interaction with provable side-effect bounds. If safe behavior cannot be established before connection, do not connect; choose a separately approved non-interacting evidence method or terminate this proof path. Live-test consent already exists; technical scenario-specific scope, JIT and GO remain required, not a new general consent request.
3. **Connection-to-listener proof.** `SO_PEERCRED` identifies the peer of a connection and `GetUnitByPID` can report a manager's mapping; neither by itself establishes that the intended service owns the listening endpoint, proves the peer is the correct daemon, or ties filesystem socket inode to the kernel listener. Specify a source-backed endpoint-to-listener-to-peer-to-unit process chain under systemd socket activation and worker/fork behavior, with pinned/rechecked identities and explicit admissible peer roles. Filesystem socket inode equality alone is not proof of the kernel listener. Prove each link with validated Linux/systemd semantics and targeted fixture evidence; deny ambiguous workers, socket handoff, competing listeners, stale endpoints and unattested mapping.
4. **Independent trust and consistency.** Do not use F4's earlier disputed unit/socket binding as a premise to prove itself. Explicitly derive the root, bus, process and endpoint trust anchors from independently verified facts, document the trusted-root/no privileged concurrent mount actor limitation, and test races, peer substitution, PID reuse, manager restart and namespace mismatch. PID/cgroup/systemd readings must have compatible views; any unresolved view, capability, ABI or atomicity concern blocks. Rechecks do not prove absence of arbitrary ABA.
5. **Reviewable result.** Produce a method-by-method source reference table, wire/budget and side-effect contract, exact negative fixture matrix, and explicit pass/fail decision for each chain link. Architecture, Security, Tester, Requirement, Python and DevOps review the identical hashes. If any link or side-effect proof remains unresolved, record `NOT_FEASIBLE` / `BLOCKED_UNKNOWN`, close this approach without host execution and route to the separately governed disposable-target/host-matrix option. Only a complete, approved proof can become a separately authored S3D slice; this draft grants no execution or admission.
