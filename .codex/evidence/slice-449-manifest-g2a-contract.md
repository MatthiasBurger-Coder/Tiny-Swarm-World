## Inputs and deterministic result

Accept only a strictly validated schema-1 `InstallationManifest` and schema-1 `ComponentCatalog`, with matching supported catalog versions. Revalidate and reject malformed/constructed-bypassing-validation instances, unknown schema/catalog versions, booleans masquerading as versions, duplicate service IDs or component IDs, selected services not in catalog, incompatible preset, missing selected dependencies, duplicate or ambiguous component/service mapping, mismatched selected bundle or any other invalid v1/catalog relationship. The current catalog method uses a dictionary comprehension and therefore cannot by itself prove no duplicate service IDs: explicitly check duplicates before mapping. Fail closed without resolving missing inputs, querying external state or mutating inputs.

Create an immutable snapshot of all original v1 installation data: identity, host, preset, product, requested/resolved selection and provenance, components, credential and configuration references, operation/checkpoint references and other fields; preserve their exact values and do not infer a new selection. Deep isolation matters: frozen Pydantic models can still contain mutable dictionaries; no dictionary or nested mutable object in input is shared with the returned preview. The preview must itself expose immutable nested data or defensive immutable representations, preserving order where semantically relevant.

For every selected optional service whose validated catalog kind is exactly `stack`, emit one deterministic sorted `(service_id, swarm)` policy default. Exclude foundations and non-stacks. The `swarm` value is the ADR compatibility **policy**, not evidence of current ownership or a write grant. The canonical Classic classifications in `src/tiny_swarm_world/infrastructure/adapters/lifecycle/catalog.py` are `incus` = `host-prerequisite` and `portainer` = `managed-foundation`; a contradictory or missing foundation kind fails closed. Selected `swagger` must have kind `stack`, otherwise fail closed; only then its exposure preview is `published`; if it is not selected, exposure is `NOT_APPLICABLE`, not a selected service. No arbitrary ID or unknown catalog result can select Swagger. Project, profile, route and actual owner identities are typed `UNKNOWN`/unadopted, never synthesized or adopted; no Portainer endpoint/stack/ResourceControl/fingerprint is inferred. No runtime state, capability version or deployment success is claimed. Project/profile/route/owner unknown means the object cannot be saved or presented as a complete, valid schema-2 installation.
