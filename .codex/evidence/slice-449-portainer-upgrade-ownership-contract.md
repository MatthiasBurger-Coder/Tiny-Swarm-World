# Portainer lifecycle ownership guard and recovery safety — proposal

Status PROPOSED; not executable until ADR owner, Requirements, Security, Architecture, Python, Tester and DevOps approve the recovery/checkpoint contract and S3D. Baseline `e882888486a817b9552f47a115ed000e340eb93d`. V1 Classic setup and swarm-owned stacks remain supported; this slice restricts only the Portainer management-gateway upgrade and recovery. No host admission or full Epic completion follows.

## Existing control flow and guard

`PortainerUpgradeService.run` enters recovery before normal inspect. Normal path validates manifest, inspects and validates bundle/images; the existing target-version no-op remains after those checks. Before any new checkpoint save, backup or upgrade, return a fixed safe BLOCKED result or declared `LifecycleStateError` when independent admissible persisted ownership evidence is absent. Current V1/V2 draft, list names, ResourceControl snapshot hash and `min(candidates)` are not such evidence. There is no positive ownership branch in this slice. A no-op is permitted only at the already-existing checked target-version branch, with no admission claim. Do not block unrelated V1 setup, direct Swarm stacks or other components.

`PortainerUpgradeApi.prove_update` must fail closed before its PUT without an implemented evidence capability; it must not invent one. Runtime `verify(recovery=False)` must also fail before proof PUT when directly invoked. Preserve sanitized errors and no raw endpoint, credential or JWT output. No tests contact a host.

## Recovery decision candidate — explicit approval required

Existing recovery can cancel an admitted source-only operation or restore a checked backup, but `_verify(recovery=True)` currently invokes the same unsafe PUT. Recovery must never call it without real ownership. It must not commit manifest or report `recovered` while proof remains unavailable. Proposed checkpoint extension: persist an unsettled `recovery_pending_proof` only after successful cancel/restore and read-only verification of original version, volume, endpoints, visible inventory, server/agent/swarm IDs and readiness; report fixed pending status, no proof of ownership, no manifest commit. Repeated recovery for this stage performs only read-only checks and returns pending, without repeating cancel/restore. Existing `recovering` represents potentially interrupted restore; never blindly replay it: fail closed with explicit uncertain/pending operator reconciliation, no host write until a separately reviewed reconciliation contract. Save `recovering` before mutating restore, preserve backup; if crash occurs after restore but before durable pending marker, classify uncertain, not successful. For admitted cancel, durable pre-effect uncertainty marker is also required before source restart; do not reuse a settled stage. Old checkpoints must decode unchanged; unknown/new stage fail closed in older readers. Exact enum/stage schema and transitional semantics require ADR owner, Requirement and Security approval before code. There is no automatic resolution until separate authenticated ownership proof and recovery reconciliation slices are designed. This trades automatic recovery completion and new upgrades for avoiding an unowned PUT; restoration may complete but remain pending.

## Recovery transition and crash matrix — candidate requiring final approval

The application port `application/ports/lifecycle/portainer_upgrade.py` gains an explicit `async inspect_recovery(before: PortainerObservation) -> None` read-only operation; the runtime implementation compares actual source version, volume, endpoint snapshot, visible ownership snapshot, server ID, agent ID and swarm ID, plus existing image/readiness checks. Observation equality only detects observed drift; it is not authoritative ownership or complete inventory. This operation may do existing authenticated reads and read-only readiness checks only, never proof PUT, backup, restore, checkpoint or manifest write. Fakes must implement it. Calls and exceptions must remain sanitized.

| Loaded stage | Action | Durable marker before effect | Result / interruption |
| --- | --- | --- | --- |
| admitted, no backup | Cancel source-only backup if admissible | new `cancel_in_progress` | read-only inspect, then durable `recovery_pending_proof`; return pending, never commit or recovered. Failure writing marker: no cancel. Crash/exception after marker: UNKNOWN, no automatic repeat. |
| backed_up or upgrading with verified backup | Restore checked backup | existing `recovering` | read-only inspect, then durable `recovery_pending_proof`; return pending, never commit or recovered. Marker save failure: no restore. Crash/exception after marker: UNKNOWN, no automatic repeat. |
| verified with verified backup | Same restore policy as upgrading, subject to existing checkpoint validation | `recovering` | same pending/UNKNOWN rule. |
| recovering or cancel_in_progress | read-only inspection only | retain unchanged | fixed UNKNOWN / manual reconciliation, never repeat mutation; observation cannot establish whether an interrupted effect completed. |
| recovery_pending_proof | read-only inspection only | retain unchanged | fixed pending on match, UNKNOWN on drift/error; no restore/cancel, proof PUT, manifest commit or recovered. |
| recovered (legacy settled checkpoint) | read-only inspection only | preserve historical checkpoint | report historical state unverified / UNKNOWN; do not newly claim proof or commit; mismatch/error UNKNOWN. |
| completed | existing refusal for downgrade recovery | unchanged | closed error; no new effect. |

A successfully returned cancel/restore is not yet durable completion: failed read-only inspection, failed pending-marker save, process death or uncertain save may leave either the old complete in-progress marker or the new complete pending marker visible after reopen. No save error reports success. Reopen read-only and validate the actual complete checkpoint: old in-progress means UNKNOWN with no replay; pending permits read-only pending re-entry only because the implementation attempts this write after the effect and read-only verification succeeded. A missing, malformed, ambiguous or otherwise unverifiable checkpoint means UNKNOWN. Never infer effect completion from an in-progress marker or blindly retry a write/effect. New enum values must be unsettled so `desired_images.py` and `update_journal.py` stay blocked as appropriate; older checkpoint bytes remain readable and unknown stages reject. No operator reconciliation operation is authorized here. `before` remains original checkpoint observation; source image/version, volume and readiness inspections preserve existing validation. The target-no-op and non-recovery gates remain as specified above.

ADR owner/Architecture reported conditional GO for designing a blocked upgrade and preserving recovery, not acceptance of this exact matrix; final exact-hash ADR owner and six-role reviews and S3D are required.
